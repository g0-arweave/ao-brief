AO work today tightened how HyperBEAM parses signed Arweave transactions, which means fewer trust-breaking edge cases when nodes read, check, and pass around transaction data.

## Sam on HyperBEAM

### Quick read:
Today’s main fix is about trust: when a node parses a signed Arweave transaction, it needs to preserve the exact fields that were signed. If parsing changes the shape of that data, even in a small way, verification can fail or become harder to reason about.

Sam merged a fix for two parsing cases: keeping the `format: 1` structural field out of rebuilt Arweave tags, and preserving original tag lists when normalized keys collide. In plain terms: HyperBEAM should not accidentally rewrite signed transaction data while trying to make it easier to handle.

That fits the recent pattern: small, sharp fixes around request parsing, Arweave data handling, and regression tests. The practical goal is less fragile infrastructure for AO apps that rely on signed data moving cleanly through the node.

### Why it matters:
- Builders get fewer weird edge cases when signed Arweave data is parsed and checked.
- Operators get node behavior that is easier to trust because parsing preserves what was actually signed.
- The AO stack gets a cleaner path between Arweave data and AO message handling.

### What stands out:
Good progress on reducing trust-sensitive parsing risk. The work is narrow, but it hits an important seam: signed data should round-trip exactly, especially when nodes are doing the work of checking and routing messages.
